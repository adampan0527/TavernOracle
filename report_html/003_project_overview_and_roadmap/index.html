1. 项目定位与核心使命 (Project Positioning)

TavernOracle（酒馆先知） 是一款专为《炉石传说·酒馆战棋》（Hearthstone Battlegrounds）设计的 Windows 平台实时“战术参谋长”HUD 辅助系统。

Core Metric 01
⚡ 极低时延预算 (< 15ms)
酒馆战棋单回合操作窗口通常仅有 30 秒“烧绳”倒计时，全链路（日志读取 $\to$ 状态更新 $\to$ 算法求解 $\to$ HUD 呈现）必须控制在 $15\text{ ms}$ 以内完成。
Core Metric 02
🎯 万分级决策吻合度 (85%~90%+)
为玩家在瞬息万变的战局中提供最优的买入、卖出、刷新、冻结、升本及随从战力站位建议，对标天梯万分级选手的实战水平。
Core Metric 03
🛡️ 100% 暴雪“纸笔准则”
零内存注入、零驱动挂钩、零键鼠模拟（严禁 SendInput/mouse_event），所有点击通过 WS_EX_TRANSPARENT 穿透，确保 0 封号风险。

2. 三层解耦系统架构与数据流 (3-Tier Topology)

系统采用严格解耦的三层分层架构，从源头抛弃纯计算机视觉截屏与 OCR 方案，保证零 GPU 负担与 $100\%$ 数据准确度：

Layer 1 · 数据摄取层
Power.log 流式状态机
无延迟监听客户端日志，结合 HearthDb 官方元数据映射 EntityID、随从属性、酒馆与手牌。
耗时 ≤ 5ms (捕获 2ms + 还原 3ms)
Layer 2 · 决策大脑
双模动态决策引擎
模式 A（贝叶斯后验 + 生死线 + 背包 DP）与模式 B（Set Transformer 模仿学习）高效求解。
耗时 ≤ 5ms (模式 A)
Layer 3 · 表现层
透明点击穿透 HUD
Win32 穿透渲染，在酒馆随从头顶浮现对子/核心/保命微标，顶部横条展示大局战略。
耗时 ≤ 5ms (硬件加速)
Overall Budget
全链路时延合计
$2\text{ms} + 3\text{ms} + 5\text{ms} + 5\text{ms} = 15\text{ ms}$。远低于人类视觉反应极限（约 200ms），极致丝滑。
总时延 ≤ 15ms
❓ 为什么坚决不用“纯截图 + YOLO/OCR 识别”？
  • 动画动态干扰严重：金色卡牌晃动、买怪出牌飞行动画与 BUFF 浮层会导致 CV 漏识率高达 $15\% \sim 30\%$。
  • 计算延迟高且占用显卡：截屏 + 图像模型推理带来 $300 \sim 800\text{ ms}$ 延迟，且高负荷抢占显卡算力引发游戏掉帧。
  • 官方 Power.log 优势显著：暴雪原生输出，零延迟（$0\text{ ms}$），$100\%$ 字段结构化，对客户端性能零开销。

3. 决策大脑：双模算法架构与数学建模演练

酒馆战棋每回合操作空间包含数万（$> 10^5$）个分支路径。TavernOracle 通过“基石模式 A + 进阶模式 B”互补：

模式 A · 生产级基石 (Rule & Knapsack DP)

耗时 $< 5\text{ ms}$，对标万分吻合度 $85\%+$，版本更新零秒冷启动。

贝叶斯流派后验概率：
$$P(\text{流派}_k \mid H, C, B) \propto P(C \mid \text{流派}_k) \times P(\text{流派}_k \mid H, B)$$
动作边际收益函数：
$$\Delta V(a) = w_{\text{tempo}} \cdot \Delta\text{战力} + w_{\text{scale}} \cdot \Delta\text{协同} + \text{对子加成}$$

结合千次蒙特卡洛战力生死线模拟（参考 Bob's Buddy），在金币与 7 卡位约束下运用分支定界背包算法在 5ms 内输出全局最优序列。

模式 B · 进阶增强 (Set Transformer)

耗时 $50 \sim 100\text{ ms}$，对标职业选手操作吻合度 $90\%+$。

双头神经网络架构：
$\pi(a \mid s)$：策略头输出原子动作概率分布（买/卖/刷/升）
$V(s)$：价值头回归输出终局排名预期值 ($1.0 \sim 8.0$)
  • 跨实体自注意力：编码场上 7 随从 + 10 手牌 + 酒馆区交互。
  • 机制语义向量化 (Zero-Shot)：基于卡牌机制特征编码，版本身材微调零样本泛化。

🎮 交互演算：战力生死线风控调节阀 ($P_{\text{lethal}}$ 策略突变)

拖动滑块模拟预测下回合的暴毙概率 $P_{\text{lethal}}$，观察保命权重 $w_{\text{tempo}}$ 与贪婪权重 $w_{\text{scale}}$ 的动态重平衡：

即时战力保命权重 ($w_{\text{tempo}} = 1.0 + 3.0 \times P_{\text{lethal}}^2$): 1.07
远期成长贪婪权重 ($w_{\text{scale}} = 1.0 - 0.9 \times P_{\text{lethal}}$): 0.86
🛡️ 稳态贪婪模式 (Greedy / Scaling Mode)
暴毙风险极低 (≤ 15%)。算法优先升本、寻找理财三连、锁核心高星对子，积累远期成长复利。

4. 技术栈选型方案对比 (Tech Stack Comparison)

为确保低延迟、高可靠性并最大化利用现有开源社区生态，项目规划了三种工程路径：

方案 技术栈 核心优势 劣势与代价 推荐等级
方案 A (首选主干) C# (.NET 8) + HDT 插件 直接集成 HearthDb、Bob's Buddy 蒙特卡洛引擎，仅需专注决策算法，1~2 周即可交付 MVP。 依赖 HDT (Hearthstone Deck Tracker) 作为宿主。 ★★★★★ (首推)
方案 B (现代独立版) Rust + Tauri + Webview2 脱离 HDT 独立运行，包体积 < 20MB，内存极低（< 40MB），现代暗夜电竞毛玻璃 UI。 需自行维护 Power.log 状态机和卡牌 JSON 库，开发周期约 3~4 周。 ★★★★☆ (进阶)
方案 C (算法科研原型) Python + PyTorch / DirectML 离线录像回放分析、Set Transformer 模型训练与特征验证极其便捷。 运行时内存与启动时间稍大，通常作为离线训练流水线而非前台客户端。 ★★★☆☆ (算法支撑)

5. 4 周敏捷开发与落地路线图 (4-Week Agile Roadmap)

按周推进、小步快跑，点击各卡片可切换高亮查看阶段职责与关键交付物：

Week 1: 数据链路打通 (Data Ingestion)
第 1 周 · 基础层
编写并分发 log.config 配置文件激活官方调试日志输出；接入 HearthDb 官方元数据；搭建基于事件的 Power.log 流式状态机。
🎁 本周交付物：控制台实时打印酒馆当前在售随从、手牌列表、可用铸币、英雄血量与当前酒馆星级。
Week 2: 决策算法与背包求解注入 (Brain Core)
第 2 周 · 核心算法
构建卡牌种族协同知识图谱与整型位掩码（BitMask）；集成蒙特卡洛千次战力模拟生死线阀门；实现 5ms 分支定界有界背包求解器（Knapsack DP）。
🎁 本周交付物：控制台在 30 秒绳子内实时输出全局评分最高的最优买/卖/刷/升操作序列及收益拆解。
Week 3: 透明穿透 HUD 与游戏吸附 (Presentation Layer)
第 3 周 · 表现层
基于 Win32 API 挂载 WS_EX_TRANSPARENT | WS_EX_LAYERED 实现绝对鼠标穿透；监听游戏主窗口 WM_MOVE/WM_SIZE 保持像素级吸附；渲染卡面头顶微标与顶部大局横条。
🎁 本周交付物：游戏内无闪烁半透明 HUD 悬浮窗，卡面上浮对子与核心怪微标，不干扰玩家原生鼠标拖牌。
Week 4: 天梯对局微调与双模增强 (Tuning & Deployment)
第 4 周 · 实战打磨
抓取社区万分段胜率矩阵注入贝叶斯单卡先验；对齐强势英雄技能（加里维克斯、拉法姆、阿凯等）专属节奏线；构建自解压打包安装程序。
🎁 本周交付物：发布首发 Release 安装包，开启实战天梯对局冲分，开展万分决策吻合度闭环验证。

6. 版本更迭 (Meta Drift) 与零冷启动策略

酒馆战棋每隔 2~4 周即进行平衡性补丁（随从攻血身材微调、移除/新进随从）。系统具备三级弹性解耦冷启动机制：

Stage 0 · 秒级热更
Day 0: 规则与背包 DP
卡牌属性解耦于外部 cards.json。补丁上线只需更新配置，模式 A 即刻生效，0 毫秒冷启动。
Stage 1 · 先验注入
Day 1~2: 天梯矩阵注入
自动爬虫抓取天梯高分局前 48 小时的单卡胜率与前四率矩阵，动态微调贝叶斯流派先验权重。
Stage 2 · 深度进化
Day 3+: 录像微调 (LoRA)
抓取万分选手实战 Replay 录像，在预训练主干上微调模式 B 的轻量 LoRA 适配层，强化微操站位。

7. 绝对合规底线与 15ms 零 GC 工程约束

🛡️ 绝对安全合规红线 (Compliance Rules)

  • 严禁任何键鼠模拟：严禁调用 SendInput、mouse_event 或 SendKeys 替玩家打牌。
  • 严禁内存与网络注入：不使用 OpenProcess、ReadProcessMemory，不挂载任何 DLL 注入钩子。
  • 唯一数据源：严格限定在本地文件流只读解析官方日志 Power.log。

⚡ 15ms 零 GC 编码约束 (Zero GC Standards)

  • 零短期堆分配：在 30 秒 DP 搜索循环中严禁使用 new 创建临时对象，规避 GC 掉帧。
  • 弃用 LINQ，使用内存池：采用定长结构体与 ArrayPool<T> 复用计算缓存。
  • 位运算极致加速：种族与状态标记采用整型 BitMask，协同匹配达到 $O(1)$ 复杂度。
